# Public contract versioning

The public bridge contract is intentionally small and implementation-neutral. It describes what an adapter receives and returns; it does not describe the private Omicos runtime.

## Compatibility rules

- `schema_version` uses a major/minor form such as `1.0`.
- A patch release may clarify wording or tighten validation without changing valid payload meaning.
- A minor release may add optional fields.
- A major release may remove or change fields and requires an explicit migration note.
- Generated manifests must record the contract version and the kit version.

Private deployments may reject a bundle whose contract version they do not recognize. A generated bundle must never claim production compatibility solely because its JSON validates.

## Kit 0.2 migration

Contract version 1.0 now has executable validation and an explicit bundle/installed-skill layout. The schema admits the generated `unresolved` field; the dry-run result no longer emits undeclared `request_echo`. Reproducibility contracts generated by 0.2 are complete Draft 2020-12 schemas. The CLI rejects malformed, empty, unsupported-version and missing-resource bundles before packaging or installation.

For a 0.1 scaffold, regenerate into a new directory and transfer reviewed algorithm-specific work after comparing the manifests and references. Do not overwrite a completed adapter with the new dry-run stub. Keep unresolved decisions explicit. The legacy installation script accepts `--destination`, but the destination now represents a workspace and the skill is installed under `skills/<name>/` rather than copying the entire transfer bundle there.

Readiness is reported as structural scaffold validity, declared-contract runtime readiness, and integration verification. A runtime-ready declaration does not independently validate its recorded evidence; the public CLI leaves integration verification false. No automatic migration can turn a scaffold into a working algorithm.
